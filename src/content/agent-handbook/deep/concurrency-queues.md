## 从一个看似矛盾的现象开始

一个数据分析服务要下载资料、调用模型、执行计算、保存结果。串行处理很慢，于是你把所有请求一起启动。开始几秒吞吐增加，随后出现限流、超时、重试，最后完成的任务反而更少。问题出在什么地方？

本节要建立三个区别：并发让多个任务处于进行中，并行让多个计算同时执行，背压让进入系统的工作量与处理能力匹配。它们属于通用系统原理，适用于爬虫、支付服务、批处理和 Agent 工具执行。学习后应能解释：`async` 为什么不保证更快，为什么平均吞吐够用时仍有长尾，怎样根据服务时间估计容量而不盲目增加 Worker。

## 先把时间分成等待与计算

假设一个请求需要 20 毫秒本地处理和 2 秒网络等待。若串行执行 10 个请求，时间大约是 20.2 秒。若远端允许同时处理，等待可以重叠，本地计算仍然要执行。理想情况下总耗时接近 2 秒加调度和本地计算开销；这不是 CPU 突然快了十倍，而是原本闲着的时间被其他任务利用了。

若每个请求需要 2 秒纯 Python 计算、没有可重叠等待，把它改成 `async def` 并不会创造更多 CPU。协程是在同一个事件循环里协作调度的执行单元，通常要遇到真正挂起的 `await` 才让出执行权。`await` 后面的对象若立即完成，也不一定发生切换；在协程里调用同步阻塞函数仍会卡住事件循环。[Python 协程与任务文档](https://docs.python.org/3/library/asyncio-task.html)

因此，应先看时间花在哪，再选工具。网络 I/O 可以用异步客户端；遗留同步 I/O 可以放到受限线程池；大量纯 Python CPU 计算通常考虑进程池或外部计算服务。线程共享地址空间，进程通常有独立地址空间，因此进程并行需要额外考虑序列化、数据复制与启动开销。

传统启用 GIL 的 CPython 中，同一进程通常不能让多个线程同时执行 Python 字节码，但 I/O 等待以及部分释放 GIL 的原生计算可以重叠。Python 已提供可禁用 GIL 的 free-threaded 构建，是否可用还取决于解释器构建和扩展支持。因此“Python 线程永远不能并行”与“有线程就能加速 CPU 工作”都不准确。[Python threading 官方说明](https://docs.python.org/3/library/threading.html#gil-and-performance-considerations)

## 一个请求穿过系统时，究竟在哪里排队

```mermaid
flowchart LR
    A[请求到达] -->|准入通过| Q[等待队列]
    Q -->|Worker 空闲后取走| W[执行槽位]
    W -->|占用连接或配额| R[远端服务]
    R -->|返回结果| D[完成与持久化]
    Q -.->|队列满时减速或拒绝| A
```

图中的队列不只有显式消息队列。HTTP 连接池、线程池、数据库锁、GPU 调度器里也可能排队。你把显式队列删掉，等待不一定消失，可能只是进入了不可观测的位置。

一个任务的端到端时间可拆成：准入等待、队列等待、实际服务时间和返回处理。吞吐量是单位时间完成多少任务，延迟是单个任务花多久；二者不能互相替代。系统可以通过堆积请求保持很高吞吐，同时让每个用户等很久。

## 用 Little 定律把容量与等待连起来

在长期平均可稳定估计、统计边界一致的系统里，Little 定律为：

$$
L=\lambda W
$$

这里的 $L$ 是系统内平均任务数，$\lambda$ 是平均有效到达率，$W$ 是平均逗留时间。若系统边界包含队列和执行槽位，$W$ 就包含等待和执行；若只统计队列，得到的是 $L_q=\lambda W_q$。不要把整个系统的任务数与仅执行时间混在一起。[Little 原论文](https://pubsonline.informs.org/doi/10.1287/opre.9.3.383)

可以从“任务占用时间的面积”理解它。十个任务分别停留一秒，就累计十任务秒；一个任务停留十秒，也累计十任务秒。把这段面积除以观察时长，得到平均在系统内的任务数；把任务个数除以观察时长再乘平均停留时间，也得到同一个量。长时间观察时要处理窗口边界上尚未完成的任务，不能只选快速完成者计算。

下面是教学假设。服务平均每分钟接收 6 个任务，每个任务执行 20 秒，有 4 个执行槽位。忽略其他瓶颈，理想服务容量约为每分钟 12 个任务。如果观测到平均排队 15 秒，则平均端到端时间为 35 秒：

$$
L=6\times\frac{35}{60}=3.5,\qquad
L_q=6\times\frac{15}{60}=1.5
$$

平均执行中的任务为 2 个，平均等待为 1.5 个；这完全可能，因为到达有突发、执行时间有波动。不能因为平均只占两个槽位，就断言四个槽位从未被占满。

如果到达提高到每分钟 18 个、最大处理仍只有 12 个，积压会持续增长，不能再把某一时刻的队列长度代入“稳态公式”预测有限的长期延迟。Little 定律不是让过载系统稳定的魔法，也不直接给出 P95 延迟。它需要与到达波动、服务时间分布和瓶颈测量一起使用。

## 背压不是丢弃工作，而是决定在哪里承担过载

容量不够时，只能从增加能力、减少单位工作、延后接收或拒绝一部分工作中选择。无限队列看似没有拒绝请求，却把代价变成无限延迟和内存增长。对于有截止时间的任务，排队到过期再执行甚至会浪费更多资源。

一个有界队列会在满时暂停生产者或显式拒绝，这就是向上游传递处理压力。`asyncio.Queue(maxsize=n)` 的 `put()` 可以等待空位，但它只约束这个进程的队列，不会自动限制所有服务实例的总配额。[Python 队列文档](https://docs.python.org/3/library/asyncio-queue.html)

```python
# 教学骨架：只展示有界接收与固定消费数，不包含持久化保证。
queue = asyncio.Queue(maxsize=32)

async def submit(job):
    await asyncio.wait_for(queue.put(job), timeout=0.2)

async def worker():
    while True:
        job = await queue.get()
        try:
            await run_job(job)  # 必须使用可协作的 I/O 或显式隔离计算
        finally:
            queue.task_done()
```

这段代码不表示“异常处理完成了”。`run_job` 抛异常会结束该 Worker，生产实现需要分类记录失败并决定继续消费还是触发服务退出；`task_done()` 仅调整队列的完成计数，也不会持久化业务成功。内存队列随进程退出丢失，因此它适合进程内调度；需要崩溃后恢复的工作要使用持久化任务记录。

信号量只限制同时进入某个代码区间的任务数。如果你先创建百万个协程，再在内部等待信号量，百万个待调度对象仍然存在。还要约束生产速率、队列长度和每个任务持有的资源。

## 为什么重试会把局部变慢变成全局故障

远端变慢时，请求占用槽位更久。占用更多导致新请求排队，排队触发更多超时，超时触发重试，重试进一步增加负载。这个反馈回路会让“多试几次”变成故障放大器。

因此，超时预算应覆盖整条调用链；剩余预算不足时不再启动新尝试；重试次数、退避与随机抖动需要有上限。更根本的是先判断调用是否能安全重试，这要进入 R2 的副作用与幂等语义。取消本地等待也不保证远端计算被取消，资源回收属于 R3 的运行状态问题。

## 自测：把概念用于判断

<details><summary>异步客户端耗时仍然很长，是否说明 asyncio 无效？</summary>

不一定。它主要改变等待重叠和本地并发能力，无法消除远端限流、连接池排队或 CPU 密集的同步解析。应分别记录排队、连接获取、远端响应和本地处理时间，再找限制总完成率的环节。只看端到端时间，无法知道瓶颈是否已经从本地转移到远端。

</details>

<details><summary>把 Worker 从 4 个增到 40 个，什么时候有收益？</summary>

当原先的槽位限制了可重叠工作，且远端、内存、连接池与数据库仍有余量时，可能有收益。若所有 Worker 竞争同一个 GPU 或相同全局 API 配额，增量主要成为排队、上下文切换和超时。应画吞吐、P95、错误率随并发度变化的曲线，选择可接受区间，而不是只比较一次最快运行。

</details>

<details><summary>每秒成功接收 10 个任务，平均延迟 3 秒，平均在系统内有多少任务？</summary>

在同一稳定统计边界下约为 30 个。如果这里的“延迟”只包含服务执行，不含排队，那么只能推出平均执行中的任务数，不能推出总积压。若大量请求被拒绝，计算队内任务时应使用真正进入该系统的到达率，而不是客户端尝试次数。

</details>

## 回到知识图：这一节连接哪里

操作系统中的调度与 I/O 解释“为什么能重叠等待”；R1 把它转成容量与排队模型；R2 解释重试是否安全；R3 解释取消或进程崩溃后谁负责剩余工作。对于 Agent，工具调用和模型请求是这些机制的应用；对于推理 Infra，GPU 批处理、KV 显存与调度形成不同的资源瓶颈。它们共享排队思想，但增加 Agent Worker 不等于增加模型推理吞吐。
