## 为什么同一句话换一个模型，token 数就不同

**教学问题：** 输入是一段普通文字，模型处理的却是整数序列。同一个中文词，有时对应一个 token，有时被拆成几个片段。是不是 token 越接近完整词，模型就越聪明？

要回答它，先把表示过程拆开：tokenizer 决定文字如何离散化，embedding 把离散编号变为向量，模型层再让向量吸收上下文。本节属于“模型输入与表示”，是概率预测与 Transformer 之前的入口。读完应能解释词表大小、序列长度和表示学习之间的取舍。

```mermaid
flowchart LR
    T[原始文字] -->|按约定规范化与预切分| U[待编码片段]
    U -->|使用固定词表和规则| I[token ID 序列]
    I -->|查可学习向量表| E[输入 embedding]
    E -->|位置与模型层计算| H[上下文化 hidden state]
    H -->|输出层与 softmax| P[下一 token 分布]
    P -->|选择 ID 再解码| O[生成文字]
```

这里有两种“模型”：分词工具里的 BPE model 是离散切分规则，大语言模型是进行表示和概率计算的神经网络。名称相同，不代表训练或职责相同。

## 一、为什么不直接按字或按词处理

按字符切分，基本单元少，但序列可能很长。按完整词切分，常用表达可能更短，但词形变化、代码标识符、专有名词和新词会让词表持续增长。遇到词表之外的字符串时，还要有处理办法。

子词方法在这两者之间取舍：常见片段用较大的单元，罕见表达拆成较小单元。byte-level 方法从字节出发，配合合适设计可以覆盖任意字节序列；某些其他分词器则有未知词标记或 byte fallback。不能只看到“BPE”三个字，就假设所有实现的基础单位、规范化和回退行为完全相同。

token 通常不是语言学意义上的词。它可以是一个词、一段词缀、空白与词的组合，也可能只对应某个 Unicode 字符的部分字节。因此“一个汉字等于一个 token”只是某些输入中的偶然现象，不应作为上下文预算公式。

## 二、用一个自造语料理解 BPE

下面忽略字节和词边界细节，假设已经把语料分为独立单词：`ab` 出现 5 次，`abc` 出现 2 次，`abd` 出现 1 次。初始词表只有 `a,b,c,d`，每个字符都是一个 token。

统计相邻符号对时，`a b` 出现 8 次，`b c` 出现 2 次，`b d` 出现 1 次。先合并最高频的 `a b`，增加 token `ab`。语料从 `[a,b]`、`[a,b,c]`、`[a,b,d]` 变为 `[ab]`、`[ab,c]`、`[ab,d]`。

再统计，`ab c` 出现 2 次，`ab d` 出现 1 次，于是下一步可增加 `abc`。每次合并减少某些序列的长度，同时扩大词表。

| 阶段 | 词表大小 | 这个小语料的总 token 数 |
| --- | ---: | ---: |
| 单字符初始状态 | 4 | 19 |
| 合并 a 与 b | 5 | 11 |
| 再合并 ab 与 c | 6 | 9 |

这些是按上面语料手算的演示数据，不是实际语言的压缩率。真正训练 tokenizer 时还要处理词边界、并列频次、基础字母表和特殊 token。使用时应用训练好的合并规则及其优先级，不是临时对每个输入重新统计频率。[Hugging Face BPE 教程](https://huggingface.co/learn/llm-course/chapter6/5)

这个例子也说明分词器与训练分布有关：经常出现的结构更容易获得较大的 token。若某种语言、代码形式或专业术语在分词训练中覆盖较少，相同内容可能被切成更多片段，影响上下文容量和计算量，但不能仅凭 token 数断言该语言的模型能力。

## 三、词表更大，为什么不总是更好

词表大小记为 V，隐藏维度记为 d，输入 embedding 表通常有 `V × d` 个参数。V 增大，常见文字可能变成更短的序列，但 embedding 表和输出类别空间也变大。若输入与输出层共享权重，可以节省一部分参数，具体要看模型架构。

**容量算例：** V=50,000、d=4096 时，一个 embedding 表有 204,800,000 个参数；以每参数 2 字节估算，约为 409.6 MB。把词表翻倍会让这个表的参数翻倍，而不会让整个模型所有层都翻倍。另一方面，序列变短可能减少注意力与缓存成本。

因此要同时考虑参数、序列长度、语料覆盖和训练效率。更大的词表还可能给很多低频 token 分配独立参数，却没有足够样本把它们学好。tokenizer 设计不是单纯追求最少 token，而是整个模型资源分配的一部分。

## 四、ID 只是地址，embedding 才是模型可学习的数值表示

假设 `科学` 的 ID 为 173，`模型` 的 ID 为 902。902 大于 173，不表示它更复杂，也不存在有意义的编号距离。输入 embedding 是从表 E 中取出对应行：

$$
e_t=E[\operatorname{id}(token_t)]
$$

这个查表等价于用 one-hot 向量乘以 E，但实现不必真的创建很大的 one-hot。训练时梯度可以更新被使用的向量及网络其他参数。词表编号和参数表之间的对应关系必须保存一致；换了 tokenizer 的 ID 映射却继续使用原来的参数表，相当于把词义地址接错。

输入 embedding 与 hidden state 也不同：同一个 token ID 的初始向量通常相同；经过注意力和前馈网络后，某一位置的 hidden state 依赖这次上下文。比如“苹果”位于水果语境和公司语境时，初始查表可能相同，但后续表示可以不同。

检索里的 embedding 又是一种使用方式：系统需要把整段文本映射成适合相似度比较的向量，通常涉及池化、训练目标和归一化。不能直接取任意生成模型中间层的一个向量，就假设它天然适合语义检索。

## 五、容易被忽略的输入协议

完整 tokenizer 流程可能包含规范化、预切分、子词编码与后处理。大小写转换、Unicode 规范化、空格和特殊符号的处理会影响输出；对于代码、数学表达式或逐字还原任务，某些规范化可能删除重要区别。具体流程可对照 [Tokenizers 官方说明](https://huggingface.co/docs/tokenizers/pipeline)。

BOS、EOS、PAD 等特殊 token 的含义也依赖模型约定。对话模型还需要将 system、user、assistant、工具内容组织成训练时使用的格式。聊天模板不是装饰：角色边界、结束标记和生成起点会改变条件输入。模型权重、tokenizer、特殊 token 配置和模板应作为一组版本资产管理。

“字符串里写了 system”不意味着宿主应该把它当作有系统权限的指令。分词和模型输入协议负责表示，权限仍由应用控制。这个边界对检索内容、工具输出和用户输入同样重要。

## 六、一个最小学习实验

选定本地已有模型配套的 tokenizer，对同一组文字记录 token ID、可视化 token、解码结果与长度。样本至少包括中文术语、英文词形变化、代码、数字、空格和少见字符。不要根据肉眼猜“应该切成几份”。

然后比较删去重复内容、变换格式前后的 token 数，以及信息是否仍完整。这个实验不调用模型就能完成，但只能说明编码变化；若要判断输出质量，还要固定模型和任务，进行后续评测。也不要把某个 tokenizer 上的 token 数直接套用到另一个模型的计费或长度限制。

## 自测与答案

<details>
<summary>1. 词表中两个 ID 很接近，是否说明语义相近？</summary>

不说明。ID 是查表索引，语义关系来自训练得到的表示及其使用方式。即使把所有 ID 做一致置换，只要 tokenizer、输入表和输出层同步置换，模型的对应行为原则上可以保持不变。

</details>

<details>
<summary>2. 为什么更大的词表可能同时省计算和增加参数？</summary>

更大单元可能缩短序列，从而减少部分注意力、缓存及生成步骤；但更多离散类别需要更大的向量表和输出空间。实际收益取决于语料分布和模型结构，不能只比较词表大小。

</details>

<details>
<summary>3. 同一个词在不同句子里含义不同，究竟是哪一步发生变化？</summary>

若切分和 token ID 相同，初始 embedding 通常相同；位置处理和各层上下文计算会产生不同 hidden state。有时前后空格或分词规则本身也会改变 ID，因此实际分析先核对编码，再讨论上下文化。

</details>
