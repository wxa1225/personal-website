## 一次本地成功还缺少什么

你在自己的电脑上让研究助理跑通了任务，输出也正确。部署后却发现数据库字段不同、镜像少了依赖、远端重复提交会产生两份计算，或者模型升级后答案质量退化。一次成功运行并没有验证这些边界。

本节把测试与交付串成一条证据链：源码版本决定运行什么，测试检查哪些性质，构建形成什么产物，部署怎样引入变化，监控与回滚怎样控制失败。它适用于一般软件；大模型系统额外需要评测行为质量，不能只验证接口能返回内容。

## 测试的层次来自问题边界

单元测试适合验证一个范围明确的逻辑，例如同一幂等键配不同输入时应该拒绝。把输入设好，检查输出或状态变化，就能快速定位错误。它不需要真实模型，因为模型随机性会掩盖控制逻辑的问题。

集成测试验证组件协作，例如服务和真实数据库的唯一约束、事务回滚和迁移是否一致。用字典模拟数据库很快，却不能证明真实隔离级别下的并发行为。契约测试验证调用双方是否同意字段、状态码、错误分类和重复调用语义；两个组件各自测试通过，也可能在接口理解上互不兼容。

故障注入则主动打断流程：远端接受后丢失回执、Worker 领取后崩溃、旧 Worker 在接管后恢复。它要验证系统承诺的不变量是否仍成立，如同一意图不重复计费、有效产物不被旧结果覆盖。

离线 eval 关注行为质量：问题是否回答正确、工具是否被合理使用、结果是否满足任务目标。程序测试可以证明失败状态分类符合规则，不能证明模型会在各种任务上作出正确选择；eval 可以发现质量退化，也不能替代事务与权限测试。

| 要证明的事实 | 更合适的验证层 |
| --- | --- |
| 参数校验与状态转换符合规则 | 单元测试 |
| 数据库、对象存储和服务真实协作 | 集成测试 |
| 调用双方理解相同接口语义 | 契约测试 |
| 崩溃与重试后不破坏关键约束 | 故障注入 |
| 模型在目标任务分布上达到质量要求 | 离线评测 |

分类不是为了完成某张工具清单，而是避免用一个便宜测试证明它实际上没覆盖的事情。

## 测试应围绕不变量，而不是复述实现

假设实现把字符串转换为大写。一个测试只是再次调用同一个内部函数生成预期值，就可能和实现一起错。更有价值的是根据外部契约写输入与独立预期，或者检查必须持续成立的性质。

对于重复提交，可以断言：两次请求返回同一执行 ID，远端创建计数为 1，相同 ID 配不同输入被拒绝。对于恢复，可以断言：原执行被继续观察，没有启动新模型，产物摘要和任务输入匹配。这些结果比“某个 mock 函数调用了一次”更贴近业务保证。

测试环境还必须可重复创建和清理，避免前一个用例的状态污染下一个。pytest fixtures 支持建立测试所需状态和清理资源，但使用 fixture 本身不会保证隔离，仍需设计数据库、目录和外部资源的作用域。[pytest fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html)

## Git 提供的是可定位的源码状态

工作区里的文件、暂存区中的修改和已提交快照并不是同一个状态。提交形成可引用的版本，让你知道测试对应哪份源码，代码审查修改了什么，以及出问题后需要比较哪个版本。[Git 官方入门](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository)

但一个 Git 提交还不等于完整实验身份。模型权重、提示、数据、依赖、运行参数和评分器也可能变化。若代码相同但远端模型别名已指向新版本，就不能认为行为一定可复现。应让运行记录能关联这些重要条件。

## 从源码到部署：每一步都要交接同一个身份

```mermaid
flowchart LR
    G[源码提交] -->|在明确环境中验证| T[测试与评测]
    T -->|从通过的版本构建| I[不可变构建产物]
    I -->|记录版本与配置| D[部署新实例]
    D -->|通过就绪与业务检查| C[逐步接收流量]
    C -->|观察质量 延迟和错误| M[运行证据]
    M -->|出现退化时回退| R[已知可用版本]
```

CI 的价值是让这些检查在约定条件下自动执行并留下记录，不是只在页面上出现绿色勾。若 CI 测的是提交 A，随后部署时又临时安装不同依赖或构建了提交 B，证据链就断开了。理想流程是从通过验证的源码构建一次，给产物一个稳定身份，再把同一产物用于后续环境。

容器镜像把应用和所需用户态依赖打包，容器是运行中的隔离进程环境。它帮助减少“我的电脑有这个包”的差异，但仍依赖宿主内核、配置、外部服务和可能的 GPU 驱动，不会自动复制整个世界。[Docker 容器概念](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/)

因此，固定镜像摘要比只记一个可移动标签更便于追踪。密码和令牌应通过适当的运行配置注入，而不是写进公开源码或镜像。可复现意味着条件可说明，不是把秘密也打包进去。

## “进程活着”与“已经可以接任务”不同

进程启动后，可能还没加载模型、没连上数据库或没完成必要初始化。存活检查用来判断进程是否需要重启，就绪检查则判断是否应接收流量。把二者混为一谈，可能在下游短暂故障时反复重启健康进程，进一步放大负载。

长任务服务更新时，还要处理正在执行的工作：先停止接新任务，允许已有任务在期限内完成或持久化可恢复状态，再退出。直接终止所有 Worker，可能丢失回执或留下远端计算；这会把部署问题转成 R2 与 R3 的一致性问题。

逐步放量有助于在影响扩大前观察异常，但必须比较有意义的业务信号。错误率、P95 延迟、超时、成本和任务质量可能朝不同方向变化。只有“CPU 正常”并不能说明新版本值得继续放量。

## 回滚也有边界

把应用切回旧镜像，通常只能恢复旧代码。如果新版本已经删除数据库字段、写入旧程序不理解的数据，或者发出了不可撤销的外部操作，回滚应用不会恢复历史世界。

所以数据库迁移应考虑新旧版本短期共存，例如先增加兼容字段，再逐步切换读写，确认后最后移除旧字段。回滚路径应在上线前被设计，而不是出问题后才寻找上一个镜像。Kubernetes Deployment 的历史与回滚围绕工作负载版本进行，也不等同于自动恢复数据库和外部副作用。[Kubernetes Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)

## 自测：测试结果允许你说到哪一步

<details><summary>100 个 mock 测试都通过，能否宣布远端恢复功能已验证？</summary>

可以说明模拟条件下的控制逻辑通过了这些检查。真实远端的超时、幂等、租期和产物行为仍需契约或集成验证。报告应区分模拟故障通过、真实正常链路通过，以及真实故障恢复是否实际触发过。

</details>

<details><summary>接口返回 200，为什么仍要业务验收？</summary>

200 只按接口协议说明请求被怎样处理。返回内容可能缺字段、引用不支持结论，或远端任务仍在运行。应检查业务终态和产物契约；模型生成“已完成”尤其不能代替文件、状态与独立评分证据。

</details>

<details><summary>代码回滚了，线上仍然异常，下一步看什么？</summary>

核对实际运行的镜像与配置、数据库迁移、缓存、模型或依赖版本、进行中的旧任务和外部副作用。回滚代码只改变其中一部分。根据部署前后的版本与指标记录定位，不应不断重启来代替证据分析。

</details>

## 回到知识图：交付是把各层知识接成证据链

程序基础保证局部逻辑，存储与分布式机制保证故障下的状态，测试验证这些契约，评测验证模型行为，CI 和部署让被验证的产物进入真实环境，可观测性再把实际结果带回研发。Agent 应用和推理服务都需要这条链，但各自关键指标和需要注入的故障不同。
